## 6. Counterexample case classification

All twelve assigned cases are classified below, in ID order, plus the two
investigator-created cases. The provisional four-relation vocabulary was
designed for relations between inferential results; most FND-2 cases compare
**datasets or data-identity declarations**, for which the vocabulary is
inadequate. Where no provisional label fits without distortion, the label is
`unresolved` and a proposed data-identity relation is recorded in the final
column. The proposed alternative taxonomy (investigator proposal,
`POSSIBLE_PROJECT_CONVENTION`, not adopted) is:

- `different_data_identity` — identity-bearing content or metadata differs;
- `equivalent_under_declared_canonicalization` — same logical content;
  physical differences are removable by a declared canonicalization;
- `same_content_different_derivation` — content extensionally equal on this
  snapshot, derivation identity differs;
- `same_content_different_execution` — content equal on inspected outputs,
  execution identity differs;
- `same_identity_different_assurance` — the identity claim is the same; what
  differs is the reachable verification class;
- `underdeclared` — declarations are insufficient to classify.

Classification reasoning never uses equality or proximity of result values as
evidence of semantic identity; absent declarations are never inferred.

### 7.4 Package-specific worked examples

#### 7.4-A. Transformation DAG: `mean(log(Y))` vs `log(mean(Y))` (`FND2-11`)

Declarations: input entity `d0` = column `y24` of snapshot S1 (values
`y_1..y_n > 0`); operations `log` (elementwise) and `mean` (aggregation), both
deterministic, versions declared.

- Graph A: `d0 → [log] → d1 → [mean] → r_A` (r_A is a scalar).
- Graph B: `d0 → [mean] → m → [log] → r_B`.

Both graphs use the same operation multiset {`log`, `mean`} and the same
input. As PROV-style structures (entities, activities, usage/generation), they
are non-isomorphic: the intermediate entity of A is a vector generated by an
elementwise activity; B's is a scalar. Investigator derivation (labeled
mathematics, not a source claim): for the natural logarithm, which is strictly
concave, Jensen's inequality gives `mean(log(y)) <= log(mean(y))` with
equality iff all `y_i` are equal; hence for any non-constant data the two
results differ. Conclusion: identity of analysis data and derived results
requires the composition structure (a DAG with typed intermediate entities),
not an operation list or an informal expression string; and the check R3/R6
pattern (recompute along the declared DAG) distinguishes A from B
deterministically. Source basis: `CLM-14` (representability), `CLM-23`
(mathematics). Remaining uncertainty: none for the structural point; numeric
tolerance policy is out of scope.

#### 7.4-B. Stochastic preprocessing: PRNG version change (`FND2-10`)

Declarations: stochastic preprocessing step `f(data; g, s)` where `g` is the
generator and `s = 42` the seed; A uses generator implementation version 1, B
version 2; one fixture output coincides.

Analysis (investigator inference): a seeded generator is a function from seed
and draw index to values; two implementations are equivalent only if they
agree as functions, which one coincident fixture cannot establish (`CLM-24`).
Parallel execution adds a scheduling dependence: the mapping from draw index
to consuming record must be fixed, or identical generators still yield
different datasets. Therefore the minimum execution-identity declaration for
stochastic preprocessing is: generator family and implementation version,
seed(s) and stream/substream discipline, draw order (mapping of draws to
records), and parallel scheduling policy; software language/version alone (the
ARS `context` slot, `CLM-08`) is insufficient. Reachable verification:
recomputation under the full declaration; fixture comparison is a smoke test,
not identity evidence. Remaining uncertainty: whether particular generator
families guarantee cross-version stream stability is an empirical/vendor
question, `NOT_VERIFIABLE` here.

#### 7.4-C. Multiple imputation: two representations (`FND2-A1`)

Declared scenario: source S1 with some `not_collected` cells in `y24`; a
declared imputation method M-id (model inputs declared) with `M = 5`
completed datasets; a per-imputation analysis operation; a declared pooling
operation over the 5 per-imputation results. No pooling formula is asserted
in this report (`SRC-14` is `NOT_VERIFIABLE`); the pooling operation is
treated as an identified black-box operation with declared inputs/outputs.

- **Representation A (M derived entities + pooling activity):** five entities
  `imp_1..imp_5`, each generated by an imputation activity (or one activity
  with five qualified generations), each `wasDerivedFrom` S1; a
  `prov:Collection` with `hadMember imp_m` fixes M structurally; five analysis
  activities produce `res_1..res_5`; one pooling activity uses exactly
  `res_1..res_5` and generates `pooled`. All machinery is directly available
  in PROV-O (`CLM-15`), and PROV-CONSTRAINTS gives unique-generation and
  ordering checks (R3/R4/R7).
- **Representation B (single stacked entity):** one entity `imp_all` (long
  format with an imputation-index column) generated by one activity from S1;
  one analysis activity reads `imp_all` and emits `pooled` directly.

Comparison (investigator inference): both can carry the same information, but
A makes the identity-bearing structure explicit and checkable — M is the
collection cardinality; per-imputation lineage supports partial recomputation
and localizes a mismatch to a specific `imp_m`; the pooling activity's input
set is closed and auditable (R7 `PARTIAL`→structural part `YES`). B compresses
lineage into an intra-dataset convention (the index column), so the same
checks exist only after a profile fixes that convention; per-`m` execution
identity (seeds per imputation) has no natural slot. Neither inspected
standard states an MI representation directly (`CLM-29`), so the choice is a
`POSSIBLE_PROJECT_CONVENTION`. Serious alternative B is viable when paired
with an explicit index-column convention; A is structurally stronger for
verification. Remaining uncertainty: whether the statistical validity
constraints on pooling impose additional representation requirements —
unanswerable without `SRC-14`-class sources (`HOLD-04`).

#### 7.4-D. Private-data assurance classes (`FND2-A2`, `FND2-12`)

Declared scenario: one private dataset D (never published), canonicalization
rule declared, commitment `h = H(canonical(D))` published, derivation
declarations as in D1. Three evidence modes for the same identity claim
("analysis X used dataset with commitment h"):

| Mode                        | What a third party can check                                                                                           | What remains unverified                                                                                                     |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Public recomputation        | Content identity against `h`; re-execution of the declared derivation; selection/row-count consistency (R2, R5, R6)    | Veracity of the original measurements (no recomputation ever establishes it); anything outside the declared tuple           |
| Trusted local recomputation | That a named verifier asserts the same checks passed in their environment                                              | Everything above **plus** the verifier's honesty, competence, and environment equivalence — trust is relocated, not removed |
| Signed attestation only     | That the signer committed to `(h, claim)` at a point in time (if timestamped); consistency among multiple attestations | Content identity, derivation, selection — every property of D itself                                                        |

Assumptions flagged (not verified facts here): that `H` is
collision-resistant and that the signature scheme is unforgeable — these are
standard cryptographic assumptions whose primary sources were not inspectable
in this pass. Conclusion (supports H6): the three modes establish strictly
nested verification content; describing them with one undifferentiated
"verified" label would overstate the two weaker modes; an evidence record
should therefore carry the assurance class explicitly, orthogonal to the
identity claim (`CLM-28`). No universal disclosure requirement follows —
excluded by scope.
